# T15 · 红果检测提速方案（2026-11-01，等拍板，红果判定代码未动）

> 取证设备：Redmi K40（<内网adb地址>，1080×2400，MIUI）｜红果 com.phoenix.read
> 原始数据：`.tmpshots/hg_probe/events.txt`（v1）、`.tmpshots/hg_probe/events2.txt`（v2，521 条红果事件）
> 业界调研：两个 agent 分别核查 GKD/ad-auto/红果专属规则 与 李跳跳/SKIP/Auto.js/OCR 路线（出处见第三节）

## 一、三条结论（先给数字）

1. **「剧集切换」拿得到，而且是零成本、精准的事件。**
   红果播放器是竖向 `androidx.viewpager.widget.ViewPager`。4 次上滑切集 → 恰好 4 簇
   `TYPE_VIEW_SCROLLED`（每簇 5~6 条、跨 0.5~0.6 秒，`Scrollable:true`、`ItemCount:122`），
   非切集时段**一条都没有**。已核对 androidx 源码：ViewPager 的
   `onInitializeAccessibilityEvent` 正是设 ClassName=ViewPager、`setScrollable(canScroll())`、
   SCROLLED 时 `setItemCount(adapter.count)`，与我们读到的字段一一对应；
   官方 `R.attr#accessibilityEventTypes` 明确 **`typeViewScrolled` 必须在 config xml 里显式声明**，
   我们现在没声明，所以服务收不到它（不是拿不到，是没订）。

2. **慢和费电的大头不是截图，是「无障碍事件洪水」。**
   红果播放时 `TYPE_WINDOW_CONTENT_CHANGED` 稳定 **约 10 条/秒**（50 秒 500 条）。
   我们的 config 订阅了它，每条事件都跑一遍 `processScreen` → `collectAllTexts`
   （逐节点 `getChild` 跨进程 IPC，红果树里 60+ 条文案）。
   实测本服务进程 **红果前台 33.4% 单核**（12.5 秒窗内烧 4.18 CPU 秒），桌面空闲 **8.7%**。
   对照业界口径：事件驱动 CPU <1%，1 秒轮询 5~10%；`packageNames` 收窄能显著降 CPU。

3. **确认一条广告要 3~6.4 秒，是链路加出来的。**
   模板采样 0.9~2.6 秒/拍（按档位）× 连续 2 拍 ≥0.85 才确认 = 1.8~5.2 秒，
   确认后还固定再等 `AD_WAIT_MS=1.2` 秒才上滑。跟「几秒才能过」对得上。

## 三、业界做法调研（两条能直接改变方案的发现）

### 发现①（可能推翻「只能截图」）：别人判红果广告，判的是**正片控件变不可见**

GKD 订阅里已有红果专属规则（`id:'com.phoenix.read'`，组名「功能类-[上滑]继续看短剧」，
activityIds 含 `ShortSeriesActivity`）：

- 规则①：`[text="上滑继续观看短剧"][visibleToUser=true]` → 上滑；
- 规则②：**不看广告本体**，而是判正片控件被盖住 —— `[text="选集"][visibleToUser=false]`，
  并用 `excludeMatches` 排掉 `[text="选集"||text*="剧评"][visibleToUser=true]`、
  `[text*="剧备字"||text="全屏观看"][height>0]`、`TextView[text$="%"][length<5][height<1]`；
  `actionDelay:1000`、`actionCd:4000`、swipe `0.7H→0.3H / 200ms`。

这跟我们 10-30 的实测**完全对得上**：红果广告页时树里仍留着上一集的 60 多条文案（选集/评论/第X集都在），
我们只读了「文本在不在」，**从没读过这些节点的 `isVisibleToUser()`**。
Auto.js 红果脚本同思路：「广告界面捕获不了有价值内容，唯有『倍速』这个关键词会消失」。

→ 若 K40 上验证成立：**零截图判定，一拍 100~300ms 出结果，CPU 从 33% 掉到几乎 0**，
截图链路只留作横屏兜底。这一条是我目前看到的唯一能同时解决「慢」和「费电」的路。

### 发现②：广告浮层进不进树，取决于一个我们没开的 flag

ad-auto 的 README 明说：**必须开 `flagIncludeNotImportantViews`，否则广告浮层根本不进无障碍树**。
抓它的 config 核对：`accessibilityFlags="flagDefault|flagRetrieveInteractiveWindows|flagReportViewIds|flagIncludeNotImportantViews"`；
我们的是 `flagDefault|flagReportViewIds|flagRetrieveInteractiveWindows`，**缺这个 flag**。
（注意：发现① 不需要这个 flag，因为判的是本来就存在的正片节点。）

### 其他（与我们底线相关的行业共识）

- 李跳跳/SKIP/GKD 全是「事件 → 遍历节点 → text/vid/clickable 匹配 → performAction」，**不截图不 OCR**；
  SKIP 识别延迟默认 300ms，且可「缩小识别区域减误触」。
- **误点父容器是公开承认的坑**：SKIP 的「严格模式」就是为防止到处搜「跳过」关键词乱点；
  开屏广告 SDK 把整块容器做成可点热区（合成点击区域落在容器宽度 45%、`fullScreenClick.randomClickNum=100`）；
  社区规则普遍用 `[clickable=true][width<130 && height<130]` 限制可点祖先，
  共识是「按钮自己不可点时才向上找可点父节点」。→ 这印证了 v2.4.5 的开屏修法方向。
- OCR 路线（AutoSlide，ML Kit 中文模型）：单帧 OCR 50~150ms，但**每次仍要 takeScreenshot**（瓶颈没解决），
  且全图推理实测 0.9~1.8 秒/张。→ 我们不换。
- 完全不费 CPU 的旁路：DNS/代理屏蔽 `pangolin`/`zijieapi`/`pglstatp`，或红果官方
  「隐私政策 → 基本功能模式」（可去中插，代价是退登、金币入口失效）。
- `TYPE_WINDOW_CONTENT_CHANGED` 必须节流（ad-auto 用 300ms + **3 秒看门狗**，因为静止广告可以
  10 分钟一个事件都不发）→ 事件驱动不能当唯一触发，低频兜底轮询必须留。

## 四、方案（按「最省、最快、最不误触」排序）

### 方案 1 · 正片控件可见性翻转判广告（**强烈建议先做一次探针验证**）

- 信号：红果在前台时读树里已有的正片节点（选集 / 倍速 / 评论 / 第X集 / 剧备字 / 全屏观看）的
  **`isVisibleToUser()` 与 bounds**；「正片控件在树里但不可见」= 广告页压在上面。
- 判定：一拍即成立 + 连续 2 拍确认（防过渡帧）；配合 `actionCd≈4000` 的滑动冷却。
- 成本：**零截图**、约 40~60 行；延迟 100~300ms（现在 3~6.4 秒）；CPU 大头（截图 + 事件洪水）都能砍。
- 必须先验证的两件事（我现在**没有**K40 上的数据，不能拍胸脯）：
  1. 广告压住时这些节点是否真的 `visibleToUser=false`（而不是「仍是 true」或「整棵子树被剥掉」）；
  2. 正片正常播放时它们是否稳定 `visibleToUser=true`（否则误滑，踩底线）。
- 验证手段：**只加一行诊断日志**的探针包（不改任何判定与手势），在真广告出现时把
  `text|visibleToUser|bounds` 打出来，跟现有截图判定做同场对照。约 20 分钟出结论。

### 方案 2 · 订上 `typeViewScrolled`，把「切集」当闹钟（与方案 1 叠加）

1. config 的 `accessibilityEventTypes` 加 `typeViewScrolled`；只认「红果包 + ClassName 含 ViewPager」的一簇。
2. `TYPE_WINDOW_CONTENT_CHANGED` 从「每条都全树采集」改成 **300ms 节流 + 3 秒看门狗**（照抄 ad-auto 的成熟做法），
   或干脆从 config 里去掉它、只留 `typeWindowStateChanged`。
3. 复核免费：自己上滑后 1 秒内等到 SCROLLED 簇 = 页面真换了 = 跳过成功。
- 预计：这是让 33.4% 掉下来的那一刀（方案 1 若成立，还顺带省掉截图）。
- 风险：静止广告不发事件 → 低频兜底轮询必须留着（从 0.9~1.8 秒降到 3~4 秒）。

### 方案 3 · 只加「切集唤醒」，不动事件订阅

~30 行，风险最低，延迟能进 1~2 秒档；但 10Hz 事件洪水还在，CPU 基本不降。适合当 2 的第一步。

### 方案 4 · 开屏/广告浮层可见性的补充开关（可选）

config 再加 `flagIncludeNotImportantViews`（1 行）：广告浮层节点更可能进树，
GKD 规则①「上滑继续观看短剧」这条 text 也才可能直接命中。
代价：树变大、每秒事件更多，必须与方案 2 的节流一起做，否则 CPU 反向上升。
另一个必须一起处理的点：现在的 `detectAdFor`（关键词命中就上滑的遗留链路）在红果上一直不触发，
是因为广告文案不进树；**一旦 flag 让广告文案进树，这条关键词链路会开始动手**，
要么先把它在红果上停用，要么改造成正判据——这是行为变化，不能顺手做，得你点头。

### 否决项

- 关键词/「文案塌缩」判广告：红果树是旧页面并集，**必然误伤**（业界一律叠加负判据）。
- MediaSession / 帧率（`dumpsys SurfaceFlinger --latency`）判广告：要 shell 或系统权限，服务拿不到。
- OCR 替模板匹配：见第三节，瓶颈（takeScreenshot 最小间隔）没解决，还多背一个模型。
- 按坐标盲点/盲滑：历史上就是它把用户送进京东/美团的，绝对不做。
- root/Frida/Xposed、改红果配置文件：超出「免 root、用户手机独立运行」的边界。
