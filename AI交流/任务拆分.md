## T1 数据源覆盖率与延迟实测（高，无需真机）

**背景**：B站跳过依赖 SponsorBlock 社区镜像 `bsbsb.top → bsbsb.cc → www.bsbsb.xyz`（只取 `sponsor` 分类）。实测第一个镜像偶发 `unexpected end of stream`，覆盖率决定整个功能的实际效果——用户最常看的视频类型如果没有片段数据，功能等于不存在。

**要做**：
1. 选 30–50 条有代表性的 BV（知识区长视频、游戏实况、影视解说、Vlog、动态漫/合集各若干），可以用 B站 公开接口取热门/排行榜列表拿 BV。
2. 对每条 × 3 个镜像统计：HTTP 是否 200、`sponsor` 段数、段总时长、片长、首段起点在片长的百分比。
3. 统计整体覆盖率、三镜像的一致性、单请求 P50/P95 延迟与失败类型。
4. 给结论：是否值得再加一个数据源（并说明候选为什么可行/不可行，别只列名字）。

**产出**：`T1_数据源覆盖.md`（结论 + 表格）+ `T1_数据源覆盖.csv`（原始数据）。每条数字要能复现：附当时的 curl 命令。
**验收**：覆盖率是**分子/分母**形式（例：`34/45 = 75.6%`），不是"大部分有"；失败样本列出 BV；curl 命令直接贴回终端能跑。
**接口提醒**：镜像必须带浏览器 UA，否则 403：
```bash
curl -s -A "Mozilla/5.0" "https://bsbsb.top/api/skipSegments?videoID=BV1njnn6yEMY&categories=%5B%22sponsor%22%5D"
```
返回是扁平数组：`[{"segment":[372.966,475.5],"videoDuration":566.336,"cid":...,"UUID":"..."}]`，没有 `segmentations` 这层。

## T2 纯逻辑缺陷清单（高，无需真机，只读不改）

**背景**：真机上已经抓出过 4 个逻辑类缺陷（暂停期间外推假位移、seek 落点越过片长、线程池关闭后提交任务、前台包名被自己的气泡顶掉）。这类 bug 全部集中在「时间数学」和「状态判定」，用真机一个个试非常慢（一条视频要播 6–10 分钟）。

**要做**：逐条推演并把结论写成用例表。范围**只限纯逻辑**，不碰 UI、不改代码：
- `app/src/main/java/.../BiliUiSkip.kt`：常量 `LEAD_MS=3000`、`REVEAL_LEAD_MS=6000`、`UNDO_MS=3000`、`UNDO_BACK_MS=2000`；外推 `posMs + (now - posAt)`；`skipTargetMs(seg) = min(end+300, dur-1500)`（`durMs<=0` 时不钳）；`fmt()` 是按秒 floor；多段广告（相邻段间隔 < 3 秒、段重叠、段起点 < 3 秒）；`skipped` 集合的清理时机；撤回后同段不再跳。
- `BiliPlaybackWatcher.kt`：标题→BV 的清洗与打分（首分句/前两分句/整句三轮、标题归一化、时长 ±5s）、`resolving` 与 `pendingResolve` 的竞态、会话销毁后重置已解析标题。
- `AdSkipAccessibilityService.kt` 里 `biliTicker` / `foregroundPkg` / `screenOn()` 的分支可达性（哪些路径会让 1 秒定时器静默停掉且无人重启）。

**产出**：`T2_逻辑缺陷清单.md`，每条包含：`输入(具体数值) | 期望行为 | 现有代码实际行为 | 判定(对/错/存疑) | 证据(文件+函数名)`。
**验收**：至少 20 条用例；**明确指出哪些是真 bug**（能给出触发数值），不要写"建议加强边界处理"这种空话；不能确定的标 `存疑` 并写清缺什么信息。
**红线**：不许改 `app/src/**`。要改就把条目写进 `协作提问.md` 等主 agent 处理。

## T3 用户视角更新说明（中，无需真机）

**背景**：`README.md` 是工程向的，普通用户看不懂"外推基准""落点钳制"。用户要把这个 App 发给别人/机房用，需要一份能直接转发的更新说明。

**要做**：把 v2.0.x → v2.1.1 的变化写成中文 CHANGELOG：每条一句人话（做了什么）+ 一句「你会感觉到什么」。技术细节放括号里，可选读。素材来源：`git log --oneline -20` 与 `README.md`（以实际提交为准，别自己编功能）。
**产出**：`T3_CHANGELOG.md`。
**验收**：无术语堆砌；不出现"优化了性能""提升稳定性"这类没有内容的句子——写清楚优化了什么、从多少到多少（有数字就用数字）。

## T4 开屏 / 红果分支代码审查（中，无需真机）

**背景**：B站分支这两天真机验证得多，开屏与红果分支还停留在早期验证，历史缺陷（误点 B站"取消"、连续滑动上限、输入法/小窗被当成应用切换）都出在这里。

**要做**：审 `AdSkipAccessibilityService.kt` 的 `handleSplashEvent` / `splashTicker` / `scanSplashOnce` / `processScreen` / `RE_COUNTDOWN`、红果滑动判定，以及 `MainActivity.kt` 的权限引导。找：崩溃点（空指针/越界/未捕获异常）、误点路径、节点未 recycle 造成的内存与耗电、10 秒窗口内的重复点击风险、`Settings.splashEnabled` 关闭时仍留下的定时器。
**产出**：`T4_代码审查.md`，按 `严重(会崩/会误点) / 中(耗电/偶发失灵) / 低(可读性)` 分级，每条给 `文件 + 函数名 + 问题 + 建议改法（伪码即可，不要直接改仓库）`。
**验收**：每条都能指出**具体可达路径**（什么事件序列走到这段代码），不做泛泛的风格点评。

## T5 MIUI 常驻与省电设置清单（中，无需真机）

**背景**：真机验证时反复遇到"系统显示已开启、服务实际没绑定""重装后悬浮窗权限被回退"。用户在小米/红机上用，需要一份一次性配对清单，否则功能会莫名失效。

**要做**：调研并实测口径（可用文档、`adb` 之外的公开资料，也可读现有代码看依赖哪些权限）：MIUI/HyperOS 上需要用户手动打开的设置项（自启动、省电策略"无限制"、通知使用权、悬浮窗、无障碍、后台运行），各自**不打开会掉哪个功能**，以及系统升级/重装后哪些会被重置。
**产出**：`T5_常驻调研.md`，表格形式：`设置项 | 影响哪个模块 | 不开的后果 | 用户怎么开（机型差异）| 是否会被系统重置`。
**验收**：与代码实际依赖一致（例如通知使用权是 B站监听必需的，别写成"建议开启"）；不确定的项直接标"未验证"，不要写成结论。

## T6 抖音平台可行性预研（低，无需真机）

**背景**：Roadmap 里写了抖音，但没验证过数据从哪来。B站这条链路能成立的关键是社区时间轴库；抖音如果没有等价数据源，方案要整个换掉。

**要做**：回答三个问题并给证据：① 有没有公开的"抖音视频广告时间点"数据源（社区库/官方接口）；② 没有的话，纯端侧可行方案有哪些、各自的误触风险（例如只靠界面找"跳过"文案）；③ 结论：值得做/只能做启发式/暂时别碰。
**产出**：`T6_抖音预研.md`。
**验收**：结论必须是可执行的判断（做/不做/需要什么前提），并写清哪些是实测、哪些是推测。
