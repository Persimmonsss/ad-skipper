日期：2026-11-01　设备：Redmi K40（1080×2400，Android 13 / MIUI）
包：v2.4.6（versionCode 26），带探针，不改变任何判定与手势

## 一、这一批改了什么（5 处，全部是"不报错的失效"）

### 1. 前台归属被系统窗口钉死 → 整条红果链路静默停摆（最严重）

原逻辑：只按 `AccessibilityEvent` 的包名更新 `foregroundPkg`，30 秒兜底刷新一次。
实测：红果播放器在前台时，系统框架窗口（`pkg=android`）每分钟送一次 `TYPE_WINDOW_STATE_CHANGED`，
`foregroundPkg` 被钉成 `android`，而每次窗口事件都会把 `foregroundAt` 刷新 → **30 秒兜底永远等不到**。
后果：事件过滤（`pkg != foregroundPkg` 直接 return）+ 轮询门控同时失效，
7 分钟里零巡检、零树扫描、零广告检测，日志里一条错都不报。

修法：窗口事件与每一拍巡检都以 **活动窗口** 为准；活动窗口是目标 App 就覆盖前台归属。

验证（重绑后）：
```
探针·心跳 巡检=5   前台=com.phoenix.read 活动=com.phoenix.read
探针·树#1  文案19  上滑可见=0 ay0i0t=0 渲染=false 可滚=3 表面对象=0 ...
```
心跳每 30 秒一条，前台/活动一致，巡检计数持续增长（169 → 324 / 30 秒）。

### 2. `pkg=android` 被当成"应用切换"触发开屏扫描，还会被当深链

- 开屏：`android` 进了 `SPLASH_SKIP_PKGS`，系统窗口不再起开屏扫描（原来每 250ms 刷一条
  `开屏扫描停止(active=com.phoenix.read)`，六分钟前一直在刷）。
- 深链：`maybeBlockAdDeepLink` 的系统白名单补上 `android`。原来滑动后 5 秒守护期内只要系统窗口
  冒一次就会被判"跳到别的 App"，**真的按一次 BACK**，会把用户从播放器里踢出去。

### 3. 开屏 ticker 自己把自己续上

`scanSplashOnce` 里 `removeCallbacks(splashTicker)` 之后，`run()` 还会无条件下一次
`postDelayed` → 停止逻辑形同虚设。现在停止时置 `splashPkg = null`，`run()` 见到 null 直接不再续。

### 4. 输入法弹前台不再算深链

实测点 B站 前贴片「跳过 3」后 0.7 秒搜狗输入法上来，被当深链多按了一次 BACK。
`pkg.contains("inputmethod")` 直接放行。

### 5. 从目标 App 切出去时，开屏扫描 5 毫秒就自停（底线的反方向：漏跳）

修好前台归属之后，这个 bug 才浮出来：从红果播放器冷启动小蚕，
`开屏窗口 com.realtech.xiaocan` 之后 **5 毫秒**就是 `开屏扫描停止(active=com.phoenix.read)`——
窗口事件到了，活动窗口还没跟上，"红果在前台就停止开屏扫描"这条老规则当场把扫描关掉，
那条开屏广告再也没被扫过。

修法：切 App 头 800ms 内不做这条判断（`splashNodeClicks == 0 && now - splashWindowStart < 800`）。

验证（同一路径，红果播放器 → 冷启动小蚕）：
```
17:02:38.597 开屏窗口 com.realtech.xiaocan
17:02:45.693 开屏首击时延 +7017ms
17:02:45.694 开屏命中 text=跳过 id=com.realtech.xiaocan:id/tv_skip → 点击
17:02:49.158 开屏已关闭
```

## 二、探针数据（K40，红果 ShortSeriesActivity 正片态）

### 2.1 `contentChangeTypes` 直方图（位名已按 android-34 `javap -constants` 纠正）

5 秒窗内（正片播放、无广告）：
```
SUBTREE:20  SUBTREE:21  SUBTREE:22  SUBTREE:24(TEXT:1) ...
```
- **SUBTREE（值 1）是绝对主力，20~24 条/5 秒（≈4~5 条/秒）**
- TEXT（值 2）只有 1~4 条/5 秒
- 其余位（CONT_DESC / PANE_* / STATE_DESC）一条都没有

结论：**T15 里"滤掉 TEXT 就能砍掉事件洪水"的判断被推翻**。想省电只能做事件合并
（同一拍内多条 CONTENT 只处理一次），不能靠收窄 eventTypes。

### 2.2 `TYPE_VIEW_SCROLLED` 真的能订上，且切集可读

- dumpsys 确认：`eventTypes=[..., TYPE_VIEW_SCROLLED]`、`capabilities=161`
- 4 分钟收到 72 条，className 全是 `ViewPager`，`from→to` 与 `itemCount` 都有值
  （`18→18 items=128`；手动上滑 6 次，每次对应一簇 6 条）
- 结论：切集信号可用，且**不需要截图**就能知道"换集了"

### 2.3 正片态无障碍树（这是本轮最有价值的一条）

连续 22 拍（每 4 秒一拍）稳定复现：
```
文案19~20  可滚=3  表面对象=0  ay0i0t=0  渲染=false  上滑可见=0
控件[第39集V601x114  展开-76x49  剧评--44x59  收藏-76x51  剧评-114x51  分享-66x66]
窗口[3:home, 3:systemui, 1AF:read]
```

要点：
1. **「第X集」是可见的（V）**。上一轮在首页 feed 上看到"正剧控件根本不在树里"，那是 feed 页，
   不能代表播放器——播放器里它是实打实可见的。
2. **「选集」不在树里**。GKD 红果规则用 `[text="选集"][visibleToUser=false]` 反推广告压盖，
   在我们这台机器上**无法作为主判据**（正常播放时它也不在）。
3. **没有 SurfaceView/TextureView 进树**（表面对象=0），而 ad-auto 的"稀疏树"判据要求
   "有视频表面"。照抄会直接失效。
4. **可滚节点=3**（广告判据里的"无可滚动容器"同样对不上）。
5. 广告页独有的「上滑继续看短剧」在正片态搜不到（上滑可见=0），方向正确，但缺广告态样本。

### 2.4 CPU（探针全开，红果前台）

| 版本 | 红果前台 CPU |
|---|---|
| v2.4.5（无探针） | 33.4% |
| v2.4.6 本批（探针全开） | 37.2% |

多出来的 ~4 个点来自：`flagIncludeNotImportantViews`（节点变多）、每 4 秒一次的树探针、
`TYPE_VIEW_SCROLLED`。探针摘掉后需复测，并单独做"事件合并"优化——`processScreen`
现在被内容事件打到 **≈5 次/秒**，这是大头。

- 「上滑继续看短剧」能否直接进树（带 `flagIncludeNotImportantViews` 之后）

## 五、顺带确认的环境坑（新增到 testing-gotchas）

- **覆盖安装后 MIUI 会把无障碍清成 `null`/`0`**，而且是在"服务已启动"之后 1 秒内再清一次：
  日志出现 `服务已启动 跳跳狐 v2.4.6` 紧接 `服务已销毁`，`settings get secure
  enabled_accessibility_services` 回到 `null`。必须重做一遍硬重绑并**当场复核
  `Bound services` 与心跳日志**，不能只看装包成功。
- `dumpsys accessibility` 的 `Bound services:{}` 可能是快照早于绑定，判活看 logcat
  的「服务已启动 + 三条模板加载」更可靠。

三条生死判据的答案：
1. **「上滑继续看短剧」能直接进树，而且是可见地进树** —— 旧结论「广告一个字都不进树」是遍历深度

2. **广告压盖走的是「不可见」，不是「整棵被剥掉」**：可见节点从 131 掉到 74~103，播放器的

   （`可见160`、`上右2 底条2`）—— 这就是 v2.5.6 加 `!playerUi` 的直接依据。
3. `ay0` / `i0t` 这类资源 id 最终没用上：文案 + 分区几何已经能分开广告、正片和两种瞬态。

改完之后的实测（v2.5.5，24 轮慢速切集）：

  只能等 0.9~1.8 秒一次的兜底轮询），命中 → 划走固定 1.2 秒，划走 → 复核成功 2.1~2.5 秒

## 七、11-03 补记二：不等设备，把 234 拍真机签名拿去离线复放收紧后的判据

设备两边都卡住（Mi 10 无线调试掉线、K40 是安全锁屏 `deviceHasKeyguard=true / mTrusted=false`，
adb 划不动、`wm dismiss-keyguard` 无效），但 v2.5.6/2.5.7 的改动只动了一个布尔条件，
可以拿已经抓到的真机分区签名直接复放——脚本 `T17_判据离线复放.py`，输出 `T17_判据离线复放输出.txt`。

复放口径：`播放器控件` 与 `提示条` 两个字段按代码里同样的方式从文案推
（含「全屏观看」/ 含「上滑继续」），再走 `verticalAd = !横屏 && 提示条 && !播放器控件 && 上右>=3 && 底条>=3`。

结果（234 条签名，pid=13276 是 v2.4.6 探针包、它的「结构判定」只是恒 0 的占位字段，不算判据）：

| 对照 | 行数 | 结论 |
|---|---|---|
| v2.5.5 真判据 =1，v2.5.7 仍 =1 | 3 | 真广告帧全保留：`上右=3 底条=4 可见=74~103 全屏观看不可见`，`!playerUi` 不误伤 |
| v2.5.5 真判据 =1，v2.5.7 改判 =0 | 1 | **正是 00:50:58.356 的退场瞬态**（`可见160`、提示条与全屏观看同时可见）——收紧要打掉的就是它 |
| v2.5.7 =1 但旧字段 =0 | 3 | 全部来自 v2.4.6 探针包的真广告帧（占位字段恒 0），不是新增误判 |
| 其余（正片 / 选集面板 / 切集动画 / 首页信息流） | 227 | v2.5.7 判广告 =0，**一帧都没被新判据放进来** |

所以：v2.5.6 的 `!playerUi` 在已有样本上是**纯收益**——一条误判被否、三条真广告一条没漏、
负样本零新增。这不能替代真机复验（复放只看单帧谓词，看不到「两拍 + 挂够 700ms」的时序，
因为探针 Z 按翻转/4 秒心跳去重，连续拍采不全；追拍效果更是完全没覆盖），
但把「收紧判据会不会把真广告一起否掉」这个最担心的风险基本排掉了。

设备恢复后的复验只看三件事：真广告还在不在 700ms 内确认、退场那一拍还误不误滑、追拍把 1.9 秒压到多少。
