> ③免 root 网络层拦截 ④无障碍信号面与性能（AOSP 源码级）。关键外部证据已二次核验（见第七节）。
> 取证设备：Redmi K40（<内网adb地址>）、Mi 10。

## 一、先给结论（一句话 + 四个数字）

**别人的方案根本不是"识别广告长什么样"，而是"只认社区验证过的控件 + 一堆硬约束把自己绑死"。**
我们要改的是判据来源和约束堆叠，不是继续优化截图匹配。

| 指标 | 我们现状 | 业界档位 | 目标 |
|---|---|---|---|
| 红果确认一条广告 | 3~6.4 秒 | 首滑 1~1.2 秒（`actionDelay:1000`）、有文案每 ~2 秒重试、无文案盲滑 5 秒一轮 | **≤1.5 秒**（有文案）/ ≤5 秒（盲档） |
| 本服务 CPU（红果前台） | **33.4% 单核** | 事件驱动 + 位过滤 + 定向查询，业界口径 <10% | **≤8%**（对齐桌面空闲 8.7%） |
| 开屏跳过件命中 | 4/5（五个指定 App） | 社区 id 表覆盖穿山甲/快手/腾讯/TopOn/华为/倍孜六家 | **5/5 且深链 0** |
| 点祖先/盲点 | v2.4.5 已禁爬祖先 | **没有任何一家爬可点祖先** | 保持，再补 3 条硬约束 |

## 二、这次调研推翻了我们的 4 个判断（最重要）

1. **`isVisibleToUser` 不代表"没被广告盖住"**。AOSP 源码 `View.isVisibleToUser(Rect)` 只查：本窗口 `mWindowVisibility` + 祖先链 `alpha/visibility` + 被祖先裁剪出屏（`getGlobalVisibleRect`），**不做兄弟节点遮挡、不做跨窗口遮挡、不管 SurfaceView 内容**。
   → T15 里"用正片控件不可见判广告覆盖层"的**机理解释是错的**。GKD 那条 `[text="选集"][visibleToUser=false]` 能用，是因为**红果自己在广告态把这些控件隐藏了**（App 主动 GONE），不是因为被盖住。所以这个信号仍然可能可用，但必须当"红果主动隐藏"来验，且 GKD 自己给它配了 **3 条 excludeMatches**、`actionCd:4000`，是当**低置信兜底**用的，不是主判据。
2. **"红果广告一个字都不进树"很可能是我们自己没开 flag**。`flagIncludeNotImportantViews` 缺失时，广告 SDK 标了 not-important 的浮层节点不进树；**`uiautomator` 默认就带这个 flag** —— 这正好解释了 10-30 那次"dump 看得到、我们的树看不到"的矛盾。GKD、ad-auto、lifeiyu 三家配置里都带着它。
   → 加 flag + **枚举红果全部窗口合并扫**（不是只看 active window），「上滑继续观看短剧」这条文案很可能直接进树，截图主层就有机会整个下掉。
3. **10Hz 事件洪水无法靠 `notificationTimeout` 合并**：AOSP `AbstractAccessibilityServiceConnection.notifyAccessibilityEvent()` 里写死 **`TYPE_WINDOW_CONTENT_CHANGED` 例外，直接绕过 pending 合并全量投递**。
   → 必须自己按位过滤。框架自己的 `AccessibilityCache` 就是判 `getContentChangeTypes() & CONTENT_CHANGE_TYPE_SUBTREE` 才清子树；播放进度条刷的是 `CONTENT_CHANGE_TYPE_TEXT`。**这一刀是把 33.4% 砍下来的主刀。**
4. **v2.4.5 的方向被行业证据完全印证，但"点按钮自己"仍有残余风险**：吾爱破解对倍孜（BeiZi）SDK 的分析给出云控参数原文 —— `SKIPVIEW.randomClick`（点"跳过"的第一击有概率被 `performSyntheticClick()` 合成成广告点击，坐标与手指位置无关）、`fullScreenClick.randomClickNum`（顶层 0、部分订单 100＝全屏热区必点）。
   → 事后深链守护（我们已有 1.5 秒）不能下掉；对已知云控聚合（晓晓优选/倍孜系）应**只走 id 白名单、不走裸文案**。

## 三、开屏方案（按改动量从小到大，P0 可当天做完）

### P0 · 规则数据 + 谓词收紧（零逻辑重构，收益最直接）
1. **补社区验证过的 id 表**（GKD 默认订阅 + Lin-arm + AIsouler 实测条目，短名匹配）：
   穿山甲 `tt_splash_skip_btn`、快手 `ksad_splash_circle_skip_view`/`ksad_splash_skip_view`/`ksad_auto_close_btn`、
   腾讯 `gdt_count_down_view`/`GdtCountDownView`、TopOn `tobid_splash_skip_ll`/`tobid_splash_skip_text`/`anythink_myoffer_btn_close_id`、
   华为 `hiad_skip_text`、倍孜 `beizi_interstitial_ad_close_*`、以及 `ms_skipView`/`adgain_splash_skip_ll`/`splash_count_down_view`/`welcome_ad_view_skip`/`only_skip_rl`。
2. **文案表补变体 + 加长度上限**：`跳過`、`| 跳过`、`点击跳过`、`跳过，进入首页`、`跳过 3`（前缀匹配 + `text.length<10`）、`直接关闭`、`关闭此条广告/关闭当前广告`。
   **`contentDescription` 也要查**（社区规则里 `desc="跳过"` 出现 29 次、`desc="关闭"` 也有；很多按钮文字藏在 desc 里）。
   倒计时类：`vid` 同时含 `count` 和 `down` 且 **不含 `download`**（`vid!*="download"` 专门排掉"点击下载"假跳过）。
3. **命中硬约束（全部 AND）**：`childCount==0` **且** `visibleToUser==true` **且** 尺寸上限（大跳过件 `<200×200`，小关闭钮 `<130×130`）
   **且** 不 climb 祖先（v2.4.5 已做）。理由：热区容器必然 `childCount>0` 且宽≈屏宽，这样是从几何上排除，而不是靠运气。
4. **假跳过排除表**（GKD `excludeMatches` 思路）：候选"跳过"节点若与全屏可点容器同 bounds、或它是那个容器的唯一子节点 → **不点**；命中目标覆盖 ≥60% 屏 → 拒绝。
5. **首点延迟**：开屏窗口**前 500ms 不点**（新开源 ad-skipper 明确跳过 OEM 启动快照期——否则会去点一张已经不存在的广告，这解释了我们偶发"切回来还点"）；
   秒点还可能被广告 SDK 判定"未曝光"（AppShare 官方要求李跳跳配 `delay:1500`），所以 500~1500ms 这段不但更安全，还可能更跳得掉。

### P1 · 窗口/计数/守护对齐业界参数（改状态机，几十行）
6. `actionMaximum` 保持 2（GKD 开屏组就是 2、ad-skipper 3、SKIP 用 `clickedRect` 去重）、`actionCd≈1000ms`、`matchTime=10s` + 广告特征续期（我们已有）、**按 App 重置计数**（GKD `resetMatch:'app'`）。
7. **App 预过滤黑名单**（GKD 订阅里几百项 `enable:false`：systemui、设置、微信、QQ、输入法、桌面、浏览器、我们自己）——既省匹配开销也缩小误触面。
8. 深链守护保留 1.5 秒，但**前台归属判定加三级回退**：`windows` 里 `isActive → isFocused → rootInActiveWindow`。依据：小米设备上有实测 `mCurrentFocus=null`、无 active 窗的情况，只靠一级会误判（这是我们 K40/Mi10 都可能撞的坑）。

### P2 · 事件驱动替代 300ms 常轮询（与红果共用同一套事件层，见第四节）
### P3 · 图片型开屏（**建议这轮不做**）
业界唯一的视觉路线是新开源 ad-skipper 的分层：ML Kit 中文 OCR（~100ms/帧）→ 自训 YOLO11n（ncnn 5MB，val mAP50 0.992）→ 本地 VLM（1.5GB，2~4 秒）兜底。
但它的 README 自曝**纯合成数据首训在真实界面 16/16 全误报**，靠追加约 300 张真实 UI 负样本才压住；且 `FLAG_SECURE` 页截图全黑时视觉层直接失效。
→ 要做也只能限定"10 秒窗口内 + 右上区域 + OCR 框 <200px + 负样本清单（倒计时圆环/CTA 大按钮/'n 秒后自动进入'）"，误触风险是公开方案里最高的一层。要留到我们前两层数据稳了再议。

## 四、红果方案（先探针，再动判据）

### 第 0 步 · 探针包（只加日志、不改任何行为与手势，约 20 分钟出结论）
必须验掉的 6 件事（都是"能不能换掉截图"的生死判据）：
1. 加了 `flagIncludeNotImportantViews` 之后，广告态逐窗口 dump 全文能不能搜到「上滑」——搜不到就直接走结构判据路线；
2. 广告态时 `选集/倍速/评论/第X集` 节点的 `isVisibleToUser` 与 `visibility/alpha/bounds` 实际值（判"红果是否主动隐藏"）；
3. 广告态 10 秒内 `TYPE_WINDOW_CONTENT_CHANGED` 的 **`getContentChangeTypes()` 直方图**（SUBTREE/TEXT/PANE_APPEARED 各占几条）；
4. 切集瞬间 `TYPE_VIEW_SCROLLED` 簇与我们手势生效的墙钟差（能不能当"闹钟"用）；红果是**老 ViewPager**（我们实测 `androidx.viewpager.widget.ViewPager`），它只填 `itemCount/scrollable`，**`from/to` 索引是 ViewPager2 才填**——所以"第几集"大概率拿不到，只能当"页面换了"；
5. 正剧 vs 广告的全树文案条数分布（业界口径：正剧 96~133 条、广告 0~15 条，需在我们机型复现再定阈值，**口径必须统一**——ad-auto 就因"过滤前/过滤后"口径不一致误滑过"新剧推荐"页）；
6. 同一广告页对比 `dispatchGesture` 与 `adb input swipe` 的翻页成功率（有个仓库声称红果拦截无障碍手势，但 GKD/lifeiyu/ad-auto 三家实测 200~250ms 无障碍手势都能翻，需自证）。

### 第 1 步 · 判定层换成"文案 → 结构 → 稀疏树"三级（替代截图主层）
- **一级（最高置信、0 成本）**：`text^="上滑继续"` 且 `visibleToUser=true`。GKD/baidu0013/iz/lifeiyu 四家都用它；写成前缀匹配是因为倒计时态文案是「Ns后可继续上滑」，前缀天然不符，不会在倒计时里误滑。
- **二级（铁律护栏，只能"禁"不能"放"）**：树里有倒计时文字（`(\d+)\s*[秒sS]\s*后` 或 `广告\s*\d+s` 角标）→ **绝不动作**；正剧保护词表 `倍速/选集/热评/分享/评论/展开/暂停/下一集/第\d+集` 任一 `visibleToUser=true` → 禁滑；`锁定倍速/倍速快进/快进中` 在屏 → 禁一切滑动（倍速面板的"上滑锁定倍速"和上滑模板同形，业界实测滑出过 2.0 倍速）；触摸后 12 秒静止闸门；断网停摆。
- **三级（无文案广告的兜底，只加不改）**：具名渲染视图 `id/ttmlive_player_render_view`（业界 5 份正剧 vs 19 份广告零反例，非混淆名、改版稳）＋ 稀疏树判据（竖屏 + 全树文案 ≤30 + 有视频表面 + 无滚动容器 + 持续 800ms）。混淆短名（`ay0`+`i0t`）只当加分项、绝不当唯一判据（改版即失效，好在失效方向是漏跳不是误滑）。
- **`选集 visibleToUser=false` 只当低置信兜底**（若探针 2 成立才用），并且必须像 GKD 那样配 `excludeMatches`（剧评可见 / 备案号"剧备字"/"全屏观看" height>0 / 屏外被裁的 `%` 进度文本）＋ 5 秒一轮 + 4 秒 CD。GKD 这条规则历史上有 **3 次因版本改版误触**（详情页、剧情简介、横屏备案号），别当主判据。
- **截图从"每条都拍"降级为"横屏且结构证据不足时才拍"**（业界横屏正剧控件全隐藏时树确实无解，退到像素几何判据；注意无障碍截图返回是 **Display P3 色域**，像素判据必须先转 sRGB——这是我们模板匹配可能一直在近失配的一个未被记录的坑）。

### 第 2 步 · 手势与复核
- 档位真机 A/B：业界主流是 **0.7h→0.3h / 200ms**（GKD 多年实测，海外版注释还专门写"时间过短可能无效"→ 用 300ms）；lifeiyu 用 220ms、0.80→0.16；商品/直播面板改**上部起手** 0.60→0.03（下部起手会被商品面板吃手势）。我们现在的 500ms 慢拖是我们的保守档，**保留作兜底档**。
- 复核去截图化：不再"滑后拍照比对"，改成"下一拍广告特征是否仍在"自然复核 + 冷却双档（有文案 1~2 秒重试、无文案盲滑 4 秒 CD）+ 每波 8 次 / 总 45 秒上限 + 连续 2 次无效就停手（业界第 3 次改坐标点按"返回"，我们底线优先，宁可停）。

### 第 3 步 · 省电（和判定层同时做）
- `TYPE_WINDOW_CONTENT_CHANGED` **只处理 `& SUBTREE != 0`**（其余 TEXT 位直接丢，这是最大的一刀）；
- 连续 content 事件按 GKD 条件合并（100ms 内 + 页面已静置 5 秒 + 3 秒内没执行过动作才丢，避免把真变化当动画噪声）；
- `TYPE_WINDOWS_CHANGED` 的 `PANE_APPEARED/DISAPPEARED`（1<<4 / 1<<5）当"广告浮层出现/消失"的低成本强信号；
- **动态 `setServiceInfo()` 收窄 `packageNames`**：开屏模块需要全 App，红果只需要 `com.phoenix.read`；官方源码注释明写 `Can be dynamically set at runtime`，但改完不追溯已投递事件、MIUI 可靠性要自测（探针项）；
- 3 秒看门狗必须留（业界实测横屏静止广告可以 10 分钟一个事件都不发，纯事件驱动会整场停摆）；
- 定向查询优先于递归遍历：`findAccessibilityNodeInfosByText/ByViewId` 是服务端一次批量 IPC，逐 `getChild` 是每个节点一次 binder 往返（业界上限：`MAX_CHILD_SIZE=512`、`MAX_DESCENDANTS=4096`）。

## 五、明确否决的路（带理由，别再回头试）

1. **免 root 网络层屏蔽（VpnService + DNS 黑洞）——判负，尤其对红果**。三条硬证据：
   ① 字节家用**火山引擎 HTTPDNS**（官方口径"绕过 Local DNS，通过 HTTP/HTTPS/DoH 查询，拿到 IP 后按 IP 直连 + Host 头发请求"），我们的 DNS 黑洞根本看不见这条查询；
   ② 广告是**预加载 + 缓存**的（穿山甲错误码 `-11 缓存过期`/`-12 缓存中没有开屏广告`；荣耀 SDK 官方就建议预缓存），当次拦不生效，用户感知就是"怎么还出广告"；
   ③ 现存番茄/红果去广告方案全是 **root + LSPosed hook**（hook `checkAdAvailable` 返回无广告；红果中插开关是服务端配置字段 `shortVideoAdEnable/landscapeInsertAdEnable/enableMultiSeriesFlowAd`），**一个域名都没提**——社区真没人靠拦域名解决红果。
   另外副作用不可接受：隧道没干净拆除=目标 App 全量断网；系统同时只允许一个 VPN（会踢掉用户的加速器）；**只要过包就不息屏 CPU 归零不了**，直接摧毁我们"回桌面/息屏 0 jiffies"的基线。
2. **激励解锁型"看广告解锁本集"**：业界定论"倒计时内上滑无效，自动化只能做到倒计时结束立刻滑，约 7 秒等待是下限"；媒体报道中插"无法由用户主动关闭，强制观看 5 秒"。这类根本跳不掉，别再投时间。
3. **按坐标盲点/盲滑**：业界对无控件开屏的兜底也只在"树里存在同 bounds 节点"才点（SKIP 的 bounds 规则），纯坐标路线历史上已经把用户送进过京东/美团。
4. **裸关键词无上下文点**：轻启动被"备忘录里写了'跳过'两个字"误点过（澎湃报道），李跳跳官方文档自己承认"少数情况会误点，解决办法是把该 App 加白名单"。
5. **OCR/YOLO 当常驻引擎**：见第三节 P3，窗口限定 + 负样本齐了才议。

## 六、比改造更便宜的旁路（建议先做一次真机验证）

红果官方「隐私政策 1.2.5 **基本功能模式**」：实测者称开启后**自动退登**，"看短剧和漫剧没再遇到之前那种频繁插播广告"，代价是不能评论、账号任务/金币受限（实测 App 版本 7.1.9，非官方承诺）。
另有「我的→设置→关于红果→了解与管理广告推送」（只减定向，**剧间强制解锁贴片关不掉**）和「开屏互动操作设置」（能关掉摇一摇触发，比我们的检测更彻底）。
→ 这条路 **0 CPU / 0 root / 0 误触风险**。要不要在你机器上开一次实测（代价是退登 + 金币），这个只有你能决定。
